# Loupe v1: Fast Queryable Codebase Index (Rust)

A Rust library (with an optional daemon and MCP wrapper) for a custom coding harness. It answers
exact-text, symbol, semantic, relationship, and "whole-repo overview" queries in
milliseconds, stays fresh as files change, and returns small, token-budgeted
answers instead of whole files.

---

## 1. Goals and non-goals

### Goals
- Sub-10 ms warm queries for text, symbol, and relation lookups on repos of tens of thousands of files.
- Incremental updates: editing one file re-indexes only that file.
- A compressed, holistic **repo map** (zoomable: map -> modules -> outlines -> code).
- Freshness guarantees: results never silently reflect stale code.
- **Library-first:** a Rust crate that the future Rust harness embeds directly; the daemon and MCP server are thin wrappers over the same API.
- **Tool-call based context:** repo map, summaries, outlines, and search are fetched on demand through tools, never forced into the prompt.
- **Fully offline:** no network access required or used (embeddings run on a local model).
- **Language-agnostic:** text, token, and embedding indexes work on any text file; symbols and graph edges come from pluggable grammars and queries.
- **Embedding (semantic) search** alongside lexical and structural retrieval: AST-aware chunks, vectors cached by chunk hash, incremental updates, and fused with the other indexes.

### Non-goals (v1)
- Any version-control functionality. Git handles history, branches, and versioning; the index only reads the working tree and (read-only) git history for co-change mining.
- Precise, compiler-grade cross-reference resolution (heuristic first, SCIP later).
- Repos beyond tens of thousands of files.
- Windows support. v1 targets macOS and Linux (Unix domain sockets, POSIX file semantics). Windows is compile-checked in CI only; runtime support is post-v1.
- Multi-writer indexes. One process writes an index at a time (see 4.4); any number may read.

### Design inspirations
- **Scion (Anthropic):** server-side, always-warm, query-first; clients never materialize the repo. *(Cited from memory; re-verify the reference before quoting it externally.)*
- **LatentGraph / Latentforce:** non-syntactic edges (co-change, coupling); a graph that can be enriched. *(Same caveat.)*
- **Trigram code search (codesearch / zoekt):** regex -> trigram candidates -> verify.
- **Aider repo map:** rank symbols by graph importance to fit a token budget.

## 2. Architecture overview

```
 harness / agent
      |  (query)            ^ (short, budgeted answer + snapshot id)
      v                     |
 +-------------------------------------------------------------+
 | loupe-daemon (optional; mmap'd index, tokio)                |
 | or embedded in-process via loupe-api                        |
 |                                                             |
 |  Query planner + fusion + budget packer                     |
 |     |            |             |              |             |
 |  Text    Symbols   Graph    Embeddings   Repo map           |
 |  (tri)   (t-sit)   (CSR)    (ANN)        (Merkle)           |
 |   |        |         |          |           |               |
 |      +---- segments + manifest (content-addressed) ----+    |
 |                         ^                                   |
 |  Overlay (dirty buffers) |  Watcher + scheduler             |
 +--------------------------|----------------------------------+
                            |
                       files on disk (+ git history for co-change)
```

Key principles:
1. **Content-addressed.** Everything is keyed by blake3 hash of file content. Unchanged content is never re-indexed, and identical files at different paths share one set of index entries.
2. **Immutable segments (LSM-style).** Writes create new segments; a manifest points at the live set; background compaction merges them.
3. **Snapshots.** A snapshot = `path -> blob hash` map + list of segments. Queries run against one snapshot; swapped atomically. **Segments index blobs, not paths**; a query resolves blob hits to paths through the snapshot, so one blob may yield several paths.
4. **mmap everywhere.** Index files are read-only and memory-mapped; the OS page cache is the cache.
5. **Overlay for dirty state.** Unsaved/uncommitted edits live in a small in-memory layer merged at query time.
6. **Every answer is stamped** with a snapshot id and a staleness flag.
7. **Library-first, sync core.** The core crate (`loupe-api`) is synchronous and uses `rayon` for parallelism. `tokio` appears only in the daemon and MCP crates.

## 4. Data model and on-disk format

### 4.1 Identifiers
- `BlobId`: blake3 hash, full 256-bit everywhere. (The original draft truncated to 128 bits inside segments; the saving is a few bytes per file and it would force a prefix lookup plus collision handling when resolving a segment hit back to snapshot paths. `BlobId::short` exists if a future posting format wants it.)
- `FileId(u32)`: dense id within a snapshot (path-level).
- `LocalBlobId(u32)`: dense id of a blob within one segment. Postings use this, not `FileId`.
- `SymbolId`: `(SegmentId, u32)`; the `u32` is dense within the segment.
- Mapping chain at query time: posting -> `LocalBlobId` -> `BlobId` -> (snapshot) -> one or more `FileId`/paths.

### 4.2 Directory layout
```
.loupe/
  LOCK                     # advisory writer lock (see 4.4)
  manifest.json            # current snapshot pointer + segment list (written atomically)
  snapshots/<id>.snap      # path -> BlobId table, file metadata (size, mtime, lang)
  segments/<seg-id>/
    text.tri               # sorted trigram table (trigram -> offset,len)
    text.post              # delta-varint posting lists of LocalBlobIds
    text.tok               # identifier-token index (fst + postings)
    symbols.bin            # symbol table (fixed-width records + string heap)
    symbols.names.fst      # name -> symbol id range
    edges.csr              # CSR adjacency (offsets + targets + weights)
    chunks.bin             # AST-aware chunk table (blob, byte range, chunk hash)
    embed.vec              # quantized vectors, one per chunk (mmap'd)
    embed.ann              # ANN graph over this segment's vectors
    meta.bin               # format version, blob list, counts, per-file checksums
  cache/summaries.redb     # (level, merkle hash, prompt version) -> summary text
  cache/embeddings.redb    # (chunk hash, model id) -> vector, reused across segments
  cache/cochange.bin       # file-pair weights from git history, keyed by the HEAD it was mined at
```

### 4.3 Segment lifecycle (LSM-style)
- A batch of new/changed blobs becomes one new immutable segment.
- **Liveness is defined by the snapshot, not by segment edits.** A blob is live iff some path in the current snapshot maps to it. Segments are never rewritten when blobs die; queries filter hits through the snapshot's live blob set (a roaring bitmap per segment, derived when the snapshot loads). `meta.bin` holds no tombstones; compaction computes dead ratios from the live set.
- Queries fan out across segments and filter results by the live set.
- Background compaction merges small segments and drops dead blobs.
- Crash safety: write segment files to a temp dir, `fsync` files and directory, rename into place, then atomically replace the manifest (write temp + `fsync` + rename). Unreferenced segment directories are garbage-collected on open.
- Integrity: `meta.bin` stores a checksum for every file in the segment. Checksums are verified when a segment is first opened; a bad segment is dropped from the live set and its blobs are re-indexed.

### 4.4 Concurrency and process model
- One **writer** per `.loupe/` at a time, enforced by an advisory lock on `LOCK`. Any number of **readers** (other processes, the CLI) open the index read-only and follow manifest swaps.
- When the harness embeds `loupe-api` in-process, it is the writer. If a daemon already holds the lock, `Index::open` falls back to a read-only client of that daemon (or opens read-only), never a second writer.
- Readers pin the snapshot they started with. GC may delete a segment only when no live snapshot generation references it (epoch/refcount in-process; a grace period for cross-process readers).

## 5. Components

### 5.1 Walker (`loupe-walk`)
- Use `ignore` for gitignore-aware traversal; also respect a `.loupeignore`.
- Skip binaries (NUL-byte sniff), huge files (configurable cap), minified/generated heuristics.
- Symlinks are never followed or indexed (stricter than "only those pointing outside the root"; it also rules out cycles and double-indexing). Revisit if real repos need in-tree symlinked directories. Paths are normalized at the boundary (relative, `/`-separated); non-UTF-8 paths are skipped and counted as errors.
- Default denylist for likely secrets (`.env*`, private keys, credential files), overridable in config. Indexed content is returned to an LLM, so this is a safety default.
- Detect language by extension + shebang.
- Hash contents with blake3; compare with the previous snapshot to produce `added / modified / removed` sets. Use `(size, mtime)` to skip re-hashing unchanged files, except files modified within 2 s of the previous scan (the "racy" window, where a same-size edit in the same timestamp tick would be missed). `WalkOptions::force_rehash` bypasses the shortcut; the daemon schedules it periodically (M3).
- Files skipped as binary, large, or minified are not in the snapshot, so they are re-sniffed (first 8 KiB read) on every scan. Cheap, but a per-scan cost proportional to their count.
- Parallelize with `rayon`.

### 5.2 Text index (`loupe-text`)
- **As built (M2):** trigrams are taken over ASCII-lowercased bytes, so one posting set serves case-sensitive and case-insensitive queries and the verifier restores exactness. Trigrams containing a newline are not indexed and the planner never requires them. Candidate files are re-read with `fs::read`, not mmap: working-tree files can be truncated or edited concurrently, which would SIGBUS a mapped reader inside the harness (immutable segment files stay mmapped). Snapshot blobs with no index entry are always scanned, never silently skipped. Ranking is by match count, then path.
- Extract trigrams per blob; build sorted trigram table + delta-varint postings (consider `roaring` for dense lists).
- **Query planning:** parse regex with `regex-syntax`, derive a trigram AND/OR query (literal extraction), intersect posting lists smallest-first, then **verify** candidates with the real regex over mmap'd file contents.
- Fallback to a full scan when the regex yields no usable literals (with a guardrail/timeouts).
- Case-insensitive support via lowercased trigram table or folded postings.
- Separate **identifier-token index** (`fst`) for fast "word" and prefix queries.
- Return ranked hits: path, line range, a few lines of context, match count.
- Correctness oracle: brute-force regex scan; property-test equivalence.

### 5.3 Symbol index (`loupe-symbols`)
- **Language-agnostic by design:** a grammar registry maps extensions/shebangs to tree-sitter grammars, and definitions are extracted by data-driven query files (tags-style `.scm`). Adding a language means adding a grammar + query file, not Rust code. Grammars are feature-flagged and loaded lazily; ship a broad default set.
- Languages without a grammar degrade gracefully: text, token, and embedding indexes still work (they don't depend on language), and symbols fall back to a generic heuristic top-level declaration finder or are skipped.
- Rust, TypeScript/JavaScript, Python, and Go are used as validation fixtures, not as a limit.
- Record: name, kind, parent, visibility, byte/line range, signature text, doc comment.
- Store as fixed-width records + string heap; name lookup via `fst`.
- Produce **outlines** (signatures without bodies) directly from this table.
- References: heuristic name-based resolution (identifier occurrence -> candidate definitions, scoped by imports where cheap). Mark each edge with a confidence level.
- Later: ingest SCIP indexes where available for precise references.

### 5.4 Graph (`loupe-graph`)
Node types: file, symbol. Edge types:
- `imports` (file -> file), from import/use statements.
- `refs` (symbol -> symbol), heuristic.
- `tests` (test file -> source file), by naming convention + imports.
- `cochange` (file <-> file), mined from git history via `gix`.

Details:
- Store as CSR (offset array + target array + weight/type arrays), mmap'd.
- Edges that cross blobs (imports, refs) depend on the whole snapshot, not on one blob. They are therefore resolved at snapshot-build time from per-segment *unresolved* edge records (file -> import string, identifier occurrences), and the resolved CSR is rebuilt incrementally for the affected neighborhood. Per-segment CSR holds only intra-blob facts.
- Co-change: weight pair by `1 / files_in_commit`, skip very large commits (formatting, vendoring), decay by age. The cache records the HEAD it was mined at and is extended incrementally; repos without git history simply have no `cochange` edges.
- **Importance rank:** PageRank (power iteration) over file and symbol graphs; used for repo map selection and result re-ranking. Falls back to in-degree if the graph is empty.
- Queries: `neighbors(node, edge_types, hops, limit)`, `impact(node)` (reverse reachability).

### 5.5 Embedding index (`loupe-embed`)
- **Chunking:** AST-aware chunks from tree-sitter (function / method / class / impl level), with windowed fallback for files without a grammar. Each chunk's embedded text = path breadcrumb + signature + doc comment + body, size-capped.
- **Chunk identity:** `blake3(chunk text + chunker version + model id)`. Vectors are cached by this key, so unchanged chunks are never re-embedded, even when a file moves or is renamed. (The path breadcrumb is part of the text, so a rename changes the key; the breadcrumb is a deliberate trade-off. If rename-stability matters more, drop the breadcrumb from the hashed text and prepend it only at embed time. Decide in the M7 spike.)
- **Embedder:** a pluggable `Embedder` trait, **local inference only** (ONNX Runtime or `candle`). Model weights are bundled or loaded from a local path and never downloaded at runtime; the index makes no network calls. Model id and dimension are recorded in segment metadata; a mismatch triggers a background rebuild.
- **Model selection (M7 spike, before building the pipeline):** shortlist small, quantizable, code-oriented embedding models with a license that permits bundling; measure CPU throughput (chunks/s), memory, dimension, and recall on the eval set. Record the choice and the measurements in the repo.
- **Storage:** quantized vectors (f16 or int8) in a per-segment mmap'd file, plus a per-segment ANN graph (HNSW). Small segments use an exact flat scan. Queries search each segment, filter dead blobs, and merge the top-k.
- **Query path:** embed the query once (cache recent query embeddings; keep the model resident), search segments in parallel, return chunks with scores.
- **Scheduling:** embedding runs in the background at lower priority than text and symbol indexing, so lexical search is available immediately. Until a file's chunks are embedded, results are flagged `semantic: partial` and the query degrades gracefully to lexical + symbols. Progress (`embedded / total chunks`) is exposed in status so the harness can decide whether to wait.
- **Correctness:** ANN results are checked against exact brute-force search in tests (recall threshold).

### 5.6 Repo map and summaries (`loupe-map`)
Zoom levels:
0. **Repo map** (~2k tokens): directory skeleton, entry points, top-ranked symbols.
1. **Module summaries:** 1-3 lines per folder/module + key files + dependencies.
2. **File/symbol outlines:** signatures and docs, no bodies.
3. **Full code:** fetched on demand.

Implementation:
- **Merkle tree:** file hash -> directory hash = blake3(sorted child names + hashes).
- Summaries cached by `(level, merkle hash, prompt/version)` in `redb`; only changed paths recompute, bubbling to the root.
- `Summarizer` trait with two impls:
  - `HeuristicSummarizer` (default, deterministic): README/doc comments, top symbols, folder names.
  - `CallbackSummarizer`: hands text to the harness (LLM) and caches the result.
- `TokenCounter` trait (approximate by default: bytes/4; pluggable exact tokenizer).
- Renderer fits output to a token budget by greedy selection on importance rank (from 5.4), with optional **focus** (boost paths/symbols near a given file or query).
- Output is stable (deterministic ordering) so it can be prompt-cached by the harness. It is delivered through tool calls (`repo_map`, `module_summary`), not auto-injected.

### 5.7 Overlay (`loupe-overlay`)
- API to `put(path, bytes)` / `remove(path)` for unsaved or uncommitted edits.
- Small in-memory trigram map + symbol table built on demand with the same extractors.
- Query layer merges: overlay wins over the base snapshot for the same path. A path present in the overlay hides the base snapshot's hits for that path, including a `remove`.
- Dirty chunks are embedded lazily into a small in-memory flat index; if not ready in time, they are served lexical-only and flagged.
- The watcher's fast path (M3) reuses the overlay: a changed file is indexed into the overlay immediately (target < 100 ms), then folded into a real segment by the background job.

### 5.8 Query layer (`loupe-query`)
Primitive queries:
- `search_text(pattern, opts)`
- `search_semantic(query, k, scope?)`
- `find_symbol(name, kind?, scope?)`
- `refs(symbol)`
- `related(file | symbol, hops, edge_types)`
- `outline(path)`
- `repo_map(budget, focus?)`, `module_summary(path)`

Fuzzy find (added after M2, fzf-style): `find_files(query, limit)` and fuzzy token/symbol lookup, using a subsequence scorer (e.g. `nucleo-matcher`, pure Rust, offline) over snapshot paths and the token list; no index format change. A CLI `loupe find` prints ranked results or pipes into `fzf`. Fuzzy matching *inside file contents* is out of scope: trigrams need contiguous literals, so that need is served by regex and semantic search.

Hybrid query `query(text, budget)`:
1. Run text, token, symbol, and semantic (embedding) retrieval in parallel.
2. Fuse with Reciprocal Rank Fusion.
3. Expand 1-2 hops on the graph from top hits (imports, tests, co-change).
4. Re-rank with importance + recency.
5. Pack results (signatures + snippets) into the token budget.

Every response includes: `snapshot_id`, `stale: bool`, `semantic: full | partial | off`, `timings`.

**Staleness definition:** a hit is `stale` if (a) its file's `(size, mtime)` on disk differs from the snapshot and the overlay has not yet absorbed the change, or (b) the answer relied on a component (e.g. embeddings, graph) that lags the snapshot.

### 5.9 Daemon (`loupe-daemon`), optional
- Optional wrapper: the Rust harness embeds the index in-process through `loupe-api`; the daemon exists for CLI use and for sharing one warm index across processes.
- `tokio` runtime; Unix domain socket; length-prefixed msgpack frames.
- Lifecycle: start -> take writer lock -> load manifest -> mmap segments -> serve; background indexing keeps serving the previous snapshot until the new one is ready (`ArcSwap`).
- **Watcher:** `notify` + debounce -> enqueue changed paths -> overlay fast path, then incremental index job.
- **Verify-on-read:** before returning hits from a file, cheap `stat` (mtime + size); if changed since the snapshot, re-read that file through the overlay path or mark the hit `stale`. The basic stat check ships in M3; the fault-injection-proven guarantee lands in M9.
- **Periodic reconciliation walk** to catch missed watcher events (platform quirks, overflowed event queues).
- Scheduler: prioritize files touched recently or requested by queries; throttle CPU/IO; run embedding jobs at lower priority than text/symbol indexing.
- The library API (`Index::open(path)`) is the primary interface; the daemon and MCP server wrap the same handlers.

### 5.10 MCP-style tool surface (`loupe-mcp`)
- Exposes the query layer as tools over stdio (JSON-RPC), so any MCP-capable agent can use the index, and the future Rust harness can reuse the same tool definitions and schemas.
- Tools: `search_text`, `search_semantic`, `find_symbol`, `refs`, `related`, `outline`, `repo_map`, `module_summary`, and hybrid `query`.
- Repo context is **pull-based**: nothing is auto-injected. The agent calls `repo_map` (token budget + optional focus) for orientation, then `module_summary` / `outline` to zoom in.
- Tool schemas derive from `loupe-proto` types (e.g. via `schemars`), so the library, socket, and MCP surfaces cannot drift apart.
- Every tool accepts a token `budget` and returns `snapshot_id` and `stale`.
- Tool descriptions are written for the model: when to use each tool, and which cheap tool to try first.

Each milestone ends with a demo and a benchmark/test gate. Dependencies are explicit: a milestone only relies on earlier ones.

## 7. Performance targets (initial, to validate)

| Metric | Target |
|---|---|
| Warm literal/regex query p50 | < 5 ms |
| Warm query p99 | < 30 ms |
| Symbol lookup | < 1 ms |
| Semantic query p50 (query already embedded) | < 10 ms |
| Query embedding (cache miss) | Measured in M7 spike; reported separately from search time |
| Background embedding throughput | Measured in M7; must not starve text/symbol indexing; full-repo embedding time reported for tens of thousands of files |
| `repo_map` render (cached) | < 20 ms |
| Single-file edit -> visible in queries | < 100 ms (via overlay) |
| Cold index (text + symbols), tens of thousands of files, laptop | < 30 s (embeddings excluded; they finish in the background) |
| Resident memory | Dominated by page cache; heap kept small |

Treat these as hypotheses; adjust after M2 benchmarks.

**M2 measurements (21.6k files, macOS laptop):** very rare literal 1.4 ms, alternation 3.2 ms, rare literal 9 ms, regex with literals 9 ms, case-insensitive literal 15 ms, common literal (4k matching files) 85 ms, full scan 712 ms; ripgrep took 660-905 ms on the same queries. The < 5 ms p50 target holds only for highly selective queries; see docs/progress.md for why and what to try. Cold text index: 6.5-9 s, 42 MB on disk, ~450 MB peak RSS.

## 8. Testing and evaluation

### 8.1 Correctness
- **Property tests (`proptest`):** text index results == brute-force regex scan.
- **Golden tests (`insta`):** symbol extraction, outlines, repo map output per language.
- **Fault injection:** kill the process mid-write; corrupt/truncate segment files; verify recovery and that bad segments are detected via checksums.
- **Concurrency:** queries during snapshot swaps and compaction; a second process attempting to open for write.
- **ANN recall:** compare ANN top-k to exact brute-force search; enforce a minimum recall.
- **Fuzzing:** regex planner and parser extraction on malformed input.

### 8.2 Usefulness (task-level eval)
- Mine real repos' history: for multi-file fix commits, query = commit message or issue title, ground truth = files changed.
- Metrics: recall@k of changed files, tokens returned, latency.
- Compare arms: `ripgrep` only vs text-only index vs semantic-only vs full hybrid (text + symbols + semantic + graph + map).
- The harness is built in M2 with the first two arms and gains arms as milestones land, so every later "beats baseline" exit criterion is measured on a fixed task set.
- Hold out a test split of tasks; do not tune fusion weights on it.
- This directly tests the claim that structural indexing pays off mainly on multi-file changes.

### 8.3 Benchmarks
- Corpora: a very large C repo, a large Rust repo, a TS monorepo, plus your own projects (capped to the tens-of-thousands-of-files scale for v1 gates).
- `criterion` microbenchmarks for posting-list intersection, regex planning, PageRank, map rendering.
- End-to-end latency histograms (p50/p95/p99), exported as metrics.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Heuristic references are noisy | Store confidence; rank by it; add SCIP later; never present as certain |
| Tree-sitter grammar upkeep / binary size | Feature-flag grammars; load lazily; generic fallback for languages without one |
| Summary cost and staleness | Heuristic default; cache by Merkle hash; LLM summaries opt-in |
| Embedding cost and model drift | Cache by chunk hash + model id; incremental only; model id in segment metadata; background, low priority |
| Embedding quality on code / ANN recall loss | Code-oriented model; AST-aware chunks; measure ANN recall vs exact; flat scan for small segments |
| Local embedding model size/speed on CPU; license | M7 spike measures throughput and checks the license permits bundling; small quantized model; batched background inference; weights loaded from a local path |
| Cross-blob edges break content-addressed reuse | Store unresolved edge records per segment; resolve at snapshot build (5.4) |
| Two processes corrupt the index | Single-writer advisory lock; readers pin snapshots (4.4) |
| Index returns secrets to the LLM | Secret-file denylist by default; symlink containment (5.1) |
| Compaction/GC complexity | Ship M1-M8 with simple "rebuild when fragmented"; real compaction in M10 |
| Repos beyond the target scale (tens of thousands of files) | mmap + lazy loading; per-directory partial indexing; file size caps; not a v1 gate |
| Watcher misses events (platform quirks) | Verify-on-read `stat` check + periodic reconciliation walk |
| Index/agent skew (stale grounding) | Snapshot ids, stale flags, overlay for dirty files, re-read before trusting signatures |
| Platform differences | macOS + Linux are v1 targets; normalize paths early; Windows compile-checked in CI |

## 10. Decisions

1. **Name:** Loupe. Crates are `loupe-*`; the index directory is `.loupe/`; the ignore file is `.loupeignore`.
2. **Harness:** will be written in Rust, later. The index is a library crate first (`loupe-api`); the daemon and CLI are thin wrappers.
3. **Repo context delivery:** tool-call based. The repo map, summaries, and outlines are pulled on demand through tools, not auto-injected into context.
4. **Scale:** tens of thousands of files for now. Mmap and segment design leave room to grow.
5. **Offline:** fully offline. Local embedding model only, no network calls from the index.
6. **Languages:** language-agnostic design. Text, token, and embedding indexes work on any text; symbols and graph use pluggable grammars and queries with graceful fallback.
7. **MCP:** an MCP-style tool surface (`loupe-mcp`) in addition to the native Rust API and the socket protocol.
8. **Platforms:** macOS and Linux for v1; Windows deferred.
9. **Async boundary:** core is sync + `rayon`; `tokio` only in daemon/MCP.
10. **On-disk records:** `zerocopy` for fixed-width structs; no `rkyv`.
11. **Concurrency:** one writer per index, many readers.
12. **Liveness:** defined by the snapshot's live blob set; no per-segment tombstones.
